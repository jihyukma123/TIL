  → Approval Gate

  → Phase 경계 검증
  → 다음 Phase
  → Workflow 완료
  →→→→ 전체 과정에서 State(현재 진행 위치 갱신) + Audit(질문, 결정, Artifact, 검증, 승인 이력)을 계속 기록

## scope

어떤 stage를 실행하고 어떤 stage는 건너뛸지(execute/skip) 미리 정의해 둔 프리셋/코스

- feature 스코프: 기획~배포까지 모든 단계를 돈다
- mvp 스코프: 운영/배포 단계는 건너뛰고 핵심 기능 구현까지만 빠르게 실행
- bugfix 스코프: 기획/시장 조사 같은 단계는 다 건너뛰고 `분석 -> 수정 -> 테스트`만 실행

## phase

정의: 소프트웨어 개발 수명주기를 구성하는 가장 큰 5개의 영역(대분류)

각 단계별로 목적과 핵심 Output이 정의되어 있음.

### INITIALIZATION: 작업을 시작할 수 있는 환경 준비

AI-DLC workflow를 실행할 수 있도록 project환경을 초기화 하는 것

- 작업 기록을 저장할 디렉터리를 구성
- workspace가 greenfield인지 brownfield인지 탐지하고
- 언어, framework, build system 등의 프로젝트 정보를 확인
- workflow 상태와 audit 기록을 초기화하고
- 선택된 scope에 따라 실행할 stage를 결정

outcome: configured workspace ready for workflow
(workflow -> 하나의 사용자 의도(Intent)를 처리하기 위해 AI-DLC가 실행하는 전체 작업 흐름)

### IDEATION — 무엇을 왜 해야 하는지 검증

목적은 제안된 initiative가 실제로 추진할 가치와 실행 가능성이 있는지 확인하는 것

- 사용자의 intent와 해결하려는 문제를 명확히 하고
- 필요한 경우 시장과 대안을 조사하고
- 기술적·사업적 feasibility와 제약을 검토하고
- 포함할 범위와 제외할 범위를 결정하고
- 필요한 팀 구성과 초기 UX 방향을 검토하고
- 진행 여부에 대한 승인을 받음

outcome: Approved initiative brief

해결할 문제, 목표, 범위, 주요 제약과 추진 방향이 정리되고 관계자가 진행을 승인한 기획 문서

이 단계가 끝났을 때는 **무엇을 왜 만들 것인가**에 대해서 human approval이 완료된 상태

모호한 intent를, Inception에서 요구사항과 설계를 구체화해도 될 만큼 검증되고 승인된 initiative로 전환하는 과정

“고객 문의 대응을 자동화하고 싶다.” -> “누구의 어떤 문제를 해결하기 위해 무엇을 만들며, 성공을 어떻게 판단하고, 이번 작업에서 어디까지 다룰지 관계자가 검토하고 승인했다.”

아니 근데 이니셔티브가, '추진 과제'라는 뜻인데 왜 굳이 산출물이 'initiative brief'지?
-> 추진 과제 자체가 산출물인게 아니라, 추진 과제의 목적/범위/성공 기준 등을 정리한 승인/인계용 문서

`initiative-brief.md`로 종합하고 사용자 승인을 받음. (presents a go/no-go gate 아하 게이트라고 하는구나 이거를.)

요약 문서 느낌으로 말하는 이유는 아직 엄청 구체화되지는 않은 상태이기 때문

### INCEPTION - 승인된 방향을 실행 가능한 계획으로 구체화

목적은 Ideation에서 승인된 initiative를 개발팀이 실제로 구현할 수 있는 수준의 요구사항과 계획으로 정밀화하는 것

- 기존 codebase가 있다면 구조와 기술을 분석
- 기능 및 비기능 요구사항을 정의
- user story와 mockup을 구체화
- domain과 application architecture를 설계
- 시스템을 독립적으로 개발 가능한 Unit of Work로 분해
- Unit 간 contract와 dependency를 정리
- 구현 순서, Bolt, 팀 배치와 위험을 포함한 delivery plan 생성

outcome: Detailed execution plan
-> 무엇을 어떤 구조로 나누어 어떤 순서와 계약에 따라 구현할지 정리된 상세 실행 계획

Ideation이 **“무엇을 왜 만들 것인가”**를 승인하는 단계라면, Inception은 **“그것을 어떻게 나누고 어떤 순서로 만들 것인가”**를 결정하는 단계

### CONSTRUCTION - 계획을 동작하고 검증된 소프트웨어로 구현

목적은 Inception에서 정의된 요구사항과 실행 계획을 실제 소프트웨어로 만드는 것

- 기능 동작과 domain rule을 상세 설계하고
- 성능, 보안, 확장성, 신뢰성 등의 NFR을 정의·설계하고
- infrastructure와 배포 구조를 설계하고
- source code와 test code를 생성하고
- build와 test를 실행하여 결과를 검증하고
- 필요한 CI pipeline과 quality gate를 구성합니다.

outcome: Working tested code
-> 요구사항에 맞게 실제로 동작하며 build/test 통과한 코드

따라서 단순히 코드가 작성된 상태가 아니라, 실행 가능하고 검증된 구현물이 핵심 결과입니다.

### OPERATION — 구현된 시스템을 배포하고 운영 가능한 상태로 유지

목적은 Construction에서 만든 소프트웨어를 실제 환경에 배포하고, 관찰·대응·개선할 수 있는 운영 체계를 만드는 것

- deployment pipeline을 구성하고
- 실행 환경과 infrastructure를 준비하고
- 시스템을 배포하고 정상 동작을 확인하고
- metrics, logs, traces, dashboards와 alarm을 구성하고
- 장애 대응 절차와 runbook을 준비하고
- 성능과 운영 요구사항을 검증하고
- 운영 결과와 사용자 feedback을 다음 개선 cycle에 반영합니다.

outcome: Production system with monitoring
-> 실제 운영 환경에 배포되어 있으며 상태를 관찰하고 장애에 대응할 수 있는 production system

여기서 결과는 단순히 “배포 완료”가 아닙니다. 배포된 시스템과 이를 지속적으로 관찰·운영할 수 있는 체계까지 갖춘 상태를 의미

### Five-Phase Structure

| Phase | Purpose | Key Outcome |
|-------|---------|-------------|
| **INITIALIZATION** | Bootstrap — state files, directory scaffold, workspace scan, routing | Configured workspace ready for workflow |
| **IDEATION** | Validate the initiative — intent, market, feasibility, scope, team | Approved initiative brief |
| **INCEPTION** | Elaborate — requirements, stories, design, architecture, units, delivery plan | Detailed execution plan |
| **CONSTRUCTION** | Build — functional design, NFRs, infrastructure, code, tests, CI | Working tested code |
| **OPERATION** | Deploy & operate — pipelines, environments, observability, incidents, feedback | Production system with monitoring |


### Phase verification

phase 경계에서는 downstream 작업 전에 artifact 누락, traceability 단절, 불일치를 검사(automated check)

여기서 verification이 실패하는 경우 사람에게 이슈 리포팅을 하고 무시하고 계속할지 아니면 보완할지 물어봄

# 최종 개념 지도
- Knowledge -> Agent 가 판단시 '참고'하는 정보(특정 행동을 강제하는 것은 아님)
- Rule -> Agent가 따라야하는 행동 규칙 (ex. 개인정보는 로그에 기록하지 않는다.)

```
[작업 관리]
Space
└─ Intent
   └─ Workflow

[프로세스 구조]
Workflow
└─ Phase
   └─ Stage

[실행]
Stage
├─ Agent
└─ Artifact

[규모 조절]
Scope
├─ 실행할 Stage 결정
├─ Depth
└─ Test Strategy

[품질 통제]
Sensor
→ Reviewer
→ Approval Gate

[지속성과 추적]
State
└─ 현재 위치

Audit
└─ 전체 이력

[조직 학습]
Knowledge
├─ 참고 정보
└─ Rule
   └─ 반드시 지킬 행동

Learning Loop
└─ 이번 작업의 교정을 다음 작업에 재사용
```

따라서 AI-DLC의 핵심 흐름은 이것으로 압축할 수 있습니다.
`Intent를 Scope에 맞는 Workflow로 변환하고, 여러 Phase와 Stage를 따라 Agent가 Artifact를 생성하며, Sensor·Reviewer·Approval Gate로 검증하고, State·Audit·Learning Loop로 진행과 학습을 보존한다.`

# Questions

**무조건 5개로 고정인지?**

ㅇㅇ

시스템 스키마 상 5개로 고정되어 있음(enum)

```javascript
phase: "initialization" | "ideation" | "inception" | "construction" | "operation";
```

stage는 플러그인/커스텀으로 자유롭게 추가 삭제가 가능하지만, phase는 sdlc의 뼈대로서 5개로 고정되어 있음.

`aidlc-principles.md` 파일에는 5개의 phase를 명시하고 있고, 
또 `aidlc-graph.ts` 같은 파일의 로직에 보면, 5개에 속하지 않는 phase값이 입력되는 경우 5개 중 하나여야 한다는 에러를 뱉는 로직이 있는 등 일단 5개는 고정이고 타협의 여지가 없음.

**모든 작업마다 반드시 5개 phase를 다 거쳐야하는지?**

ㄴㄴ 그건 아님

`04-phases-and-stages.md` 문서를 보면, 예를 들어서 4번 Operation phase의 경우 mvp/poc/bugfix/refactor scope에서는 이 전체 페이즈를 건너뛰어도 된다고 언급되어 있음.

다만 initialization은 모든 intent에서 항상 실행됨(그 이유는 Workspace 생성·탐지와 state 초기화가 필요하기 때문)
-> 모든 predefined scope에서 Initialization phase의 3개 stage는 항상 실행됨

**verification이 automated check인데, 그러면 phase 건너갈때 사람의 approval이 없이 자동 검증으로 넘어가나?**

좀 이상하다 싶어서 물어봤는데, 애초에 프로세스가, 

phase의 마지막 stage는 무조건 사람의 명시적 승인을 받도록 되어 있음
-> 승인 이후에 automated check로 넘어가는 구조인 것.

명확히 말하면 로직이 다음과 같음

endOfPhase이기 때문에 approval을 요구하는 것이 아니다. 모든 비-Initialization 실행 stage가 기본적으로 approval 대상이고, endOfPhase 판정은 별도로 phase 검증과 전이를 작동시킨다.
-> humanapproval은 end of stage라서 발생, 그 이후에 endofphase인 경우에는 automated check 수행

```javascript
const needsApproval = stage.phase !== "initialization";

const endOfPhase =
  !nextStage || stage.phase !== nextStage.phase;

if (needsApproval) {
  await askHumanApproval();
}

if (endOfPhase) {
  await runPhaseBoundaryVerification();
}
```

**엔진이 따라가는 path는 어떤 단계에서 만들어지나?**

실제 작업별 path는 Initialization의 0.3 State Initialization에서 만들어집니다.

```javascript
const scope = selectAndConfirmScope(userRequest);
const graph = loadCompiledStageGraph();

const path = graph.map(stage => ({
  stage,
  action: scope.includes(stage) ? "EXECUTE" : "SKIP"
}));

saveToState(path);
start(firstExecutableStage(path));
```
즉:
- 설치 시 모든 stage와 연결 관계를 stage-graph.json으로 미리 컴파일
- 작업 시작 시 scope를 선택하고 사용자 확인
- Initialization 0.3에서 각 stage를 EXECUTE/SKIP으로 결정
- 결과를 aidlc-state.md에 저장
- 엔진이 이 계획에서 다음 EXECUTE stage를 차례로 선택

실행 중 scope 변경이나 recompose를 승인하면, 아직 실행하지 않은 path는 다시 구성될 수 있습니다.
