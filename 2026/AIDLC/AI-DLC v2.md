## 9개의 원칙

### 1. Human judgement insights can be distilled into machines

AI-DLC 2.0은 인간의 반복적인 판단과 검증에서 패턴을 추출해 규칙, post-condition, 도구 및 결정적 executable로 점진적으로 codify할 수 있다는 전제를 둔다. 이를 지속적으로 축적함으로써 인간이 매 단계 직접 관여하는 구조에서, AI가 명확한 경계 안에서 자율적으로 실행·검증·수정하고 예외적인 상황에만 인간에게 판단을 요청하는 구조로 이동하려는 것이다.

-> 조직의 판단 기준이 시스템의 검증 계층에 계속 축적된다

즉 시간이 지나면서 경험적인 직관? 이런 것들을 축적하는 구조인거지 자꾸 흘려보내는게 아니라.

AI의 '자율성'이란, 

AI의 inherent한 능력 + 명확한 입출력 + 기계가 검사할 수 있는 조직의 판단 기준 -> 세 가지가 충족된 '안전한 작업 범위' 내에서 발휘되어야 함.

### 2. Every Intent Starts Ambiguous (and That's OK)

초기 의도의 모호함을 인정하되, AI의 명확화 질문과 구조화된 사전 준비를 통해 실제로 실행 가능한 요구사항으로 점진적으로 구체화한다.

소프트웨어 개발 요청은 모호하게 시작하고, 그게 자연스럽다는 관점임.

'영업 성과 대시보드를 만들어 줘'라는 요청에는 다음과 같은 모호함이 존재함
- 누구를 위한 대시보드인지?
- 어떤 성과지표를 보여줄 것인지

등등..

사용자는 
- 자신이 알고 있는 것을 명확하게 표현해서 AI에게 요청하기 어렵고
- 뭘 모르는지조차 모르는 unknown unknowns도 가지고 있다.

### 3. AI as a Self-Correcting Solver (with a Safety Net)

명확한 입력·출력과 신뢰할 수 있는 자동 검증 기준이 주어지면, AI는 생성·검증·수정을 반복해 스스로 유효한 결과에 수렴할 수 있다. 

다만 무한 반복을 막기 위해 횟수·토큰 등의 중단 조건을 두고, 기준이 모호하거나 정해진 한도 내에 해결하지 못할 때만 인간에게 판단을 요청한다.

기본 루프는 다음과 같음

생성
-> 결과 검증
-> 실패 원인 확인
-> 수정
-> 다시 검증
-> 성공하거나 한도에 도달할 때까지 반복

이 루프가 안정적으로 동작하려면 세 가지 조건이 필요함

1. 검증기를 AI가 마음대로 수정할 수 없어야 한다.

AI가 테스트를 통과하지 못했을 때 구현을 수정해야지, 테스트를 삭제하거나 성공 조건을 약화해서는 안됨

2. 성공 기준이 다룰 수 있는 크기여야 한다.

"좋은 시스템을 만들어라"와 같은 추상적인 기준은 수렴점을 제공하지 못함. 테스트 성공, 정책 위반 없음, 성능 임계값 만족처럼 확인 가능한 기준이어야 함.

3. 반복 비용이 충분히 저렴해야 한다.

한 번 검증하는 데 몇 시간과 막대한 비용이 든다면 많은 후보를 시도할 수 없음. 반복이 빠르고 저렴할수록 AI의 자기 수정이 실용적임.

#### Stage별로 자율화 가능한 수준의 차이가 존재함.

예를 들어, Test 단계나 Intrastructure Provisioning 단계는 기계적으로 검증하는게 비교적 수월함

- 테스트 성공 여부
- 빌드 성공 여부
- 배포 결과
- 정책 위반 여부
- 성능 임계값 측정

하지만, 사람의 가치 판단이 더 많이 필요한 단계들도 있음

- 요구사항 분석
- 디자인 검토
- 제품 우선순위
- 사용성/미적 품질

#### Safety net의 필요성

halting condition을 설정해야된다 루프에.

실패를 숨기거나 무한히 반복하지 않고, 인간이 이를 인지할 수 있게 알리고 가이드를 받아야 함.

경계가 분명히 존재하는 자율성, bounded autonomy


### 4. The Three-Compartment Model

하나의 개발 작업을 세 가지 관점으로 나눠 정의하자는 내용임.

'이거 만들어줘' 하는게 아니라, 다음 3가지 질문에 답할 수 있도록 작업을 설계하자는 것.

1. 무엇을 만들어야 하는지?
2. 제대로 만들었는지 어떻게 확인하는지?
3. 이번 작업에서 무엇을 배워 다음에 활용할 것인지?

Generate -> Verify -> Learn

만들고, 확인하고, 지식을 축적하는 flow로 가는거임.

#### Compartment 1: 무엇을 해야 하는가?

작업의 입출력을 정의하는 방식으로 AI에게 무엇을 해야하는지 제공함.

로그인 API 구현이라는 작업을 처리해야된다고 하면,

입력
- 로그인 요구사항
- 사용자 데이터 모델
- 보안 정책
- 기존 프로젝트 구조

출력
- 로그인 API 코드
- 인증 서비스
- 테스트 코드
- API 명세

'결과물까지 명시한다'가 중요한 포인트. (나도 AI에게 작업을 시킬 때 이런 식으로 해서 한 번 해봐야겠네 항상. 코딩 작업을 시킬 때는, 어떤 결과가 나와야하는지 알고 시켜야겠지. 결과를 알지만 그걸 내가 일일이 치는게 아니라 내가 원하는걸 니가 찍어내줘 가 되어야 하니까.)

이거 그리 중요한 포인트가 `선언적`이라는 점이네.

나는 내가 원하는 결과와, 그 결과를 만들기 위해서 써야되는 input만 주는 식으로 선언적으로 요청하면 그 중간에 구현은 AI가 정해진 boundary내에서 알아서 하는 바이브.

그리고 추가로, `중간 산출물도 출력으로 정의할 수 있음`

최종 결과만 요구하면 AI가 중요한 설계 과정을 생략할 수도 있음. 필요하다고 판단될 때, 품질에 중요하다고 여겨지는 중요한 중간 결과도 명시적인 출력으로 정의할 수 있음.

최종 출력
- 로그인 API 코드

필수 중간 출력
- 인증 흐름 설계
- 오류 처리 정책
- 위협 시나리오
- 구현 계획

이런 식의 접근의 특징은, '잘 설계해' 같은 식의 추상적인 지시에 비해서 더 과정을 구체적으로 지시하고 확인하는게 용이함.

다만 이건 trade off가 명확하기 때문에, 어떤 중간 산출물을 출력으로 정의할 것인지에 대해서는 잘 생각해봐야 함.


#### Compartment 2: 제대로 했는지 어떻게 아는가

결과의 성공 조건을 의미하는 'post-condition'을 정의

로그인 API의 경우 다음과 같은 조건이 될 수 있음
- 올바른 계정 정보로 로그인할 수 있다
- 잘못된 비밀번호는 거부된다
- 비활성화된 계정은 로그인할 수 없다
- 비밀번호가 로그에 기록되지 않는다
- 일정 횟수 이상 실패하면 제한된다.
- 모든 인증 테스트가 통과한다.
- 조직의 API 보안 정책을 위반하지 않는다.

이런 조건들이 있어야지 AI가 결과를 스스로 검사하고 맞춰서 수정이 가능함

결과 생성 -> post-condition check -> 실패 항목 확인 및 수정 -> 다시 검사

성공 조건은 2종류임

- Computational verification: test, linter, 정적 분석, 정책엔진 등 결정적으로 검사, 절대 어기면 안되는 조건에 적합
- Inferential verification: LLM이 자연어 규칙과 품질 기준을 바탕으로 판단. 설계 타당성/코드 리뷰 등 맥락과 뉘앙스가 필요한 작업에 적합함.

근데 한 가지 고려해야되는 부분은, 같은 모델이 결과를 만들고 다시 결과를 자연어 기준으로 평가 시 규칙의 의도보다 문구만 만족하는 결과를 낼 수 있다고 함.
그래서 LLM 판단 만으로 검증되는 stage는 LLM이 자기 판단만으로 종료하면 안되고, 인간에게 결과를 제시해야됨. 

자율적으로 LLM이 아 이거는 잘 됐어라고 평가하고 넘어가는 범위를 넓히려면? 더 많은 검증 기준을 deterministic executable로 표현해야된다.


#### Compartment 3: What did i learn?

실행 과정에서 무엇을 배웠는지에 대한 기록

- 인간이 반복적으로 수정하는 부분
- 검증에서 반복적으로 발견되는 결함
- 재실행을 유발하는 패턴
- 기존 규칙에 없는 예외
- 사용자가 accept-is-as로 승인한 상황
- 새롭게 발견된 조직의 guardrails

예를 들어 대시보드를 만들 때 사람이 반복해서 “이 색상은 브랜드 기준에 맞지 않는다”고 수정했다면:
- 관찰: 특정 색상 조합이 계속 거절됨
- 학습 후보: 조직의 UI 색상·대비 기준
- 반영: 다음부터 Compartment 2의 검증 조건으로 추가

이런 관찰을 다음 실행에 적용할 rule, exemplar 또는 post-condition 후보로 만든다.

후보로 올리면 사람이나 혹은 별도의 승인 절차를 통해서 실제 조직 표준이나 검증 조건으로 채택

### 5. Every SDLC Stage Fits the Compartment Construct

4번의 3-compartment 모델은, 코딩/테스트 뿐만 아니라 소프트웨어 개발의 모든 단계에 적용할 수 있다고 보는 것.

**요구사항 분석 단계**를 생각해보면,

입력:
- 사용자의 intent
- 기존 시스템 정보
- 이해관계자 맥락

출력:
- 기능 요구사항
- 비기능 요구사항
- 제약조건
- 가정과 미해결 질문

검증:
- 중요한 요구사항 영역이 누락되지 않았는가
- 서로 모순되는 요구사항이 없었는가
- 모든 가정에 근거가 있는가

학습:
- 사용자가 반복적으로 보완한 요구사항 패턴
- 조직에 항상 기본적으로 필요한 기본 NFR

**배포단계**도 마찬가지로,

입력:
- 배포할 artifact
- 환경 정보
- 배포 정책

출력:
- 배포 결과
- 검증 보고서
- rollback 정보

검증:
- health check 성공
- 정책 위반 없음
- smoke test 성공

학습:
- 반복적으로 발생하는 환경 차이
- 실패를 유발한 배포 조건


요점은 “창의적이거나 분석적인 일은 구조화할 수 없다”가 아니라, 그런 일도 정의된 입력을 받아 기대는 산출물을 만들고, 명시된 사후조건으로 품질을 판단하는 변환 과정으로 다룰 수 있다는 것

예를 들어, 코딩처럼 입출력과 검증 조건이 명확한 활동도 있지만, 요구사항 분석처럼 일견 그렇지 않은 활동이 있음 근데 요구사항 분석 조차도 이 generate-verity-learn 구조에 맞춰서 AIDLC-fy가 가능하다는거임.

코딩/테스트와 요구사항 분석 같은 활동의 차이는 `검증 기준의 성숙도`라고 함.

구현/테스트 -> 정량적/자동화된 검증을 빨리 갖출 수 있음
요구사항 분석/설계 비평 -> 초기에는 인간 검토가 더 많이 필요함.

인간 검토에서 얻은 기준을 compartment3를 통해서 축적하고, 이후 compartment 2의 검증 규칙으로 조금씩 옮겨가는 것이 포인트임.


### 6. Staged Decomposition over single-shot compression

한 방에 user intent -> deploy code 로 가는 것은 적절치 않다고 생각한다고 함.

이런걸 'compression'이라고 하는데, 이렇게 하면

- post-condition explosion: 너무 많은 검증조건을 한 번에 체크해야됨. 복잡할 뿐만 아니라 서로 interdepedent 해져서 거의 뭐....난리나는거지.
- combinational search explosion: ai가 여러 검증 조건을 검토해야해서, ai 실행 루프가 길어짐.

근데 v1에서는 이걸 고정된 Stage로 쪼갰는데, 이게 너무 단위도 크고 opinionated 되어 있어서 사람들이 aidlc를 도입하는데 장벽이었음.

이걸 기반으로, 더 필요에 따라 유연하게 조합 가능한 단위를 구성하는 방법을 찾았고, 그게 `skill`이라고...

뭔지 모르겠지만 무튼 skill을 적극적으로 쓰겠다는거 잘 알겠음.

무튼 독립적으로 입출력/검증 조건을 정의할 수 있는 크기로 분리를 잘해서 구성하라는 소리

### 7. Autonomous Development in Safe Increments Rather than as a Big-Bang

조직이 어느 날 갑자기 전체 소프트웨어 개발을 AI에게 맡길 수는 없다는 현실적인 원칙

갑자기 AI한테 다 해줘 이거 안된다는 소리임.

점진적으로 도입해야된다.

기업에 존재하는 제약사항

- 규제
- 보안
- 아키텍처 
- 내부 코딩 표준
- 변경 금지 영역
- 수동 검토 절차
- 암묵지(문서화되지 않은)

기계 검증 가능한 post-condition으로 전환하는 시행착오 시간이 필요함.

3단계 도입 process 제안

Start with what you have -> hydrate incrementally -> expand the safe increment size

AI를 활용한 자율 개발은 0 or 1이 아니다. -> 어디까지 AI가 자율적으로 하고 어디는 사람이 할지에 대한 영역을 탐험하고 범위를 설정해서 점차 자율적으로 처리할 수 있는 범위를 넓혀가는 것.
(Netflix 영상하고도 통하는 부분이 있는 듯? 테스트해보면서 공통화를 더 해서 사람들의 속도를 높이는 것)


### 8. Extensibility

어떤 framework도 모든 고객의 규칙·규제·업무 절차·도메인 지식을 미리 알 수 없으므로, 확장성은 나중에 추가하는 편의 기능이 아니라 처음부터 설계 제약으로 다뤄야 한다는 원칙

AI-DLC가 기본 개발 방법을 제공하되, 고객 회사의 규칙에 맞게 고쳐 쓸 수 있어야 한다.

AIDLC에 개별 사용자가 자신들의 규칙을 정식으로 추가하거나, 변경할 수 있어야 한다는 소리임.

1. 기본 규칙에 커스텀 규칙 추가
2. 기본 규칙을 커스텀 규칙으로 변경
3. 기본에는 없는 새로운 작업 추가

AWS가 모든 회사의 규칙 미리 알수도 없고 만들수도 없음. -> 제공해주는 기본 패키기 쓰되, customizable 해야한다.

### 9. Learning from Practice — Compound Engineering

Skill과 workflow는 처음 작성된 상태로 고정되는 것이 아니라, 실제 사용을 통해 계속 개선되어야 한다는 원칙

사람이 AI 결과를 고친 경험을 한 번 쓰고 버리지 말고, 다음부터 AI가 같은 실수를 하지 않도록 규칙으로 쌓아두자

일반적으로 AI를 쓰면, 사람이 AI의 결과를 검토하고 수정 요청한 내역은 보통 그 대화 내에서만 유효하고 사라짐. -> 9번 원칙에 의하면 모든, 정말 every correction is a candidate learning.

“Compound Engineering”은, 프로젝트를 할수록 조직의 규칙·체크리스트·가드레일이 누적되어 다음 프로젝트가 더 잘 되게 만든다는 의미.

`사람이 반복해서 알려준 조직의 판단 기준을 승인된 규칙으로 축적한다`

축적해서 자꾸 AI가 더 조직의 의도와 맥락을 검토 가능한 규칙으로 변환하는 과정을 통해서 장기적으로 ai를 안정적으로 fully 맥락 aware하게 사용하자.

검증도 최대한 규칙을 활용해서.

AI 요약

AI-DLC의 큰 그림은 이렇습니다.

> **처음에는 사람이 AI를 많이 이끌지만, 반복되는 사람의 판단을 규칙으로 축적해 AI가 점점 더 안전하게 자율 수행하도록 만드는 개발 방법론**입니다.

```text
모호한 의도
  → 질문으로 명확화
  → 작은 작업 단위로 분해
  → 생성·검증·학습
  → 고객 규칙에 맞게 조합
  → 수정 경험을 규칙으로 축적
  → 더 넓은 범위를 안전하게 자율화
```

9가지 원칙을 한 줄씩 정리하면:

1. **사람의 반복 판단을 규칙·도구·검사로 옮겨, AI를 계속 덜 감독하게 만들자.**
2. **처음 요구사항이 모호한 것은 정상이며, AI는 추측하지 말고 질문해서 명확히 해야 한다.**
3. **명확한 성공 기준이 있으면 AI가 생성→검증→수정을 반복하되, 한도 안에 못 풀면 사람에게 넘겨야 한다.**
4. **모든 AI 작업은 ‘무엇을 만들지(Generate)·어떻게 검증할지(Verify)·무엇을 배울지(Learn)’로 정의하자.**
5. **코딩뿐 아니라 요구사항 분석·설계·배포·운영도 이 공통 프레임으로 구조화할 수 있다.**
6. **“앱 하나 만들어줘” 같은 원샷 대신, 작은 Skill로 쪼개 필요한 것만 조합하자.**
7. **처음부터 완전자율화를 목표로 하지 말고, 검증 가능한 범위부터 안전하게 조금씩 넓히자.**
8. **AWS 기본 방식은 제공하되, 고객은 자기 회사 규칙·절차·작업 단위를 추가·교체·조합할 수 있어야 한다.**
9. **사람이 반복해서 고친 내용은 버리지 말고, 승인 후 다음부터 AI가 검사할 규칙으로 축적하자.**

이 원칙들을 역할별로 묶으면 더 잘 보입니다.

| 역할 | 원칙 | 의미 |
|---|---:|---|
| 출발점 | 1, 2 | 사람의 판단을 줄이되, 모호함은 질문으로 다룬다 |
| 작업 방식 | 3, 4, 5 | 각 SDLC 작업을 생성·검증·학습 가능한 단위로 만든다 |
| 실행 구조 | 6 | 작은 Skill들을 조합해 필요한 흐름을 만든다 |
| 도입 전략 | 7 | 검증 가능한 곳부터 자율성을 확대한다 |
| 현장 적용 | 8, 9 | 고객별 규칙을 넣고, 실제 수정 경험으로 계속 개선한다 |

결국 AI-DLC는 **“AI에게 일을 던지고 결과를 받는 방식”**이 아니라, **“AI가 일을 수행하는 과정과 검증 기준을 조직의 개발 자산으로 만들고, 그 자산을 계속 누적하는 방식”**이라고 보면 됩니다.
