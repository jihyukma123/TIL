# [물이 빠지면 누가 발가벗고 수영했는지 드러난다](https://evan-moon.github.io/2026/02/10/developer-in-ai-era/)

AI 시대에 개발자의 역할이 어떻게 달라지고 무엇을 준비해야되는지에 대하여.


질문: 동일한 결과물을 생산하고 있다고 했을 때, 그 결과물을 만드는 과정에서 우리는 시간을 어디에 많이 쓰고 있는가?
-> 이걸 보면, 뭘하고 있는지가 단편적으로 보이겠지 좋은 질문이다.

명백하지 이거는. 코드를 더이상 쓰지 않고 코드를 판단하고, 결과물을 판단하는 작업에 시간을 많이 쓰고 있다.

그 결과물을 평가하는 과정에서, 언젠간 사람이 없어질까? -> 문제가 생겼을 때 책임지는 역할의 사람은 필요하니까 있긴 해야됨..

역할 시프트가 결과물 판단, 코드 검토로 넘어가고 있다면, 

- 코드를 '잘' 생성하기 위한 프롬프트가 중요할까? 아니겠지. 그건 사실 누구나 프롬프트 잘 짜면 되니까.

개발자의 차별적인 역량은 이제 만들어진 코드를 잘 검토하는 것에 있다.

- 잘 실행되는지
- 예외처리가 잘 되었을지
- 사내 기준에 맞는지

등등.....속해있는 환경의 맥락에 맞는 코드가 생성되었는지에 대한 검증이 필요함.
-> 여기서 중요한 부분은, 결국 사람이 코드를 읽어야 한다는거고 이는 여전히 사람이 읽기 쉬운 코드를 '생산'하는 역량이 중요하다는 의미. (예전같았으면 코드를 '작성'한다라고 했을텐데 요즘은 '생산'이 더 맞는 표현인듯?)

## 장기 변경 비용 예측 역량

AI -> '동작하는 코드' 생성에 최적화 되어 있음. 돌아가긴 하는데, 문제는 프로덕션 레벨에서 함께 고려되어야 하는 유지보수성과 같은 문제는 보다 덜 고려되어 있음.

지금 작동하는 코드 -> 단기 품질, 단일 산출물의 품질
6개월 뒤 프로덕트 변화에 따라 유지보수가 용이한 코드 -> 장기 변경 비용 예측

이 2가지는 완전히 다른 문제이며, 후자를 고려해서 AI의 결과물을 다듬는 것이 개발자의 중요한 역량 중 하나인 것은 여전함.

## 코드 다각도로 평가하는 역량

테스트로 평가할 수 없는 부분을 볼 수 있어야 한다.

기능적인 부분은 어느정도 테스트로 검증이 가능함
- 동작하느냐

But 구조적 품질은 어떻게 판단할거야?
- 모듈의 책임 범위가 적절한가?
- 의존성 방향이 맞는지?
- 인터페이스가 변경에 유연한가?
- 데이터가 10배 늘었을 때 동일하게 잘 동작할 것인가?
- 보안 관련해서 여러 기준들을 충족하는가?

이런 부분들을 자연스럽게 고려하면서 코드를 평가하는 것은 단순히 '동작하네' 하고는 차원이 다른 역량임.

지금은 코드 생산 속도가, 검토 속도보다 압도적으로 빨라서 그 언밸런스에서 오는 비효율이 존재함.
-> 이런 시장 상황에서는 코드를 제대로 빠르게 검수할 수 있는 능력이 있는 개발자의 가치가 올라감.

## 추상화 역량

복잡한 전체 구조 안에서 무엇을 감추고 드러낼지, 어디에 경계를 그을지 결정하는 능력.
-> 표현이 와닿지 않네. 이해하려고 신경쓰다보면 이해되는 날이 오겠지.

AI -> 평균적으로 좋은 코드를 만들 수 있지만, 맥락에 어울리는 '최적의 코드'는 잘 찾지 못할 수 있음.

추상화라는 것은 평균적으로 좋은 방향으로 하는 것도 필요하지만, 그보다는 맥락에 맞춰서 상황에 맞춰서 적절한 추상화에 대한 그때그때 판단이 필요한데, 이 모든 고맥락을 AI한테 쑤셔넣고 코드를 만들어달라고 해도 확률적으로 잘 해낼텐데 심지어 모든, 맥락을 그렇게 AI한테 매번 제공하는 것도 거의 불가능에 가깝겠지.

앞서 말했던 경우와 비슷한데, AI가 짠 코드의 결함 혹은 부적절한 추상화로 인한 비효율은 코드가 생산되어서 평가되는 시점이 아니라, 코드를 변경해야되는 시점에 보인다고 함.

`그 추상화가 실제로 복잡도를 줄이는가? 아니면 추적해야될 간접 경로만 늘리는가?`
-> 이 질문을 던져야 한다는 것을 알고 있는 것. 이 문제를 인식하고 있는 것 자체가 역량이라고 함.

이런 관점에서 생각이 필요하겠네.

## 암묵지를 명시화하는 역량

어디에 경계를 왜 그어야 하는지 설명할 수 있는 것. 

관습적으로 하는게 아니라... '아 뭔가 이상한데....' 이런 직관은 설명하기는 쉽지 않음.

-> 이 함수는 책임의 범위가 너무 크다, 이 인터페이스는 변경되면 금방 깨질 것 같다 같은 구체적인 지시사항을 줄 수 있어야 함.

모델이 얼마나 발전하건, 변하지 않는 것은 모델이 뭘 할지는 인간이 줘야 한다는 것. 그러니까 코드를 작성하고 검토하고 수정할 때도 마찬가지로 무엇을, 어떤 이유로, 어떤 요건들을 고려해서 수정해야되는지를 알려주는 것이 역량이되겠지.

결제 시스템이 복잡한 이유는, 사용하는 프레임워크가 복잡해서가 아니라 결제 도메인이 복잡하기 때문이다. 복잡성을 다루는 역량은 도구에 종속되지 않는다.

React, Vue 이런게 아니라 복잡성을 보고 다루는 능력

## 의도적 수련 설계의 필요성

미래의 개발자에게 코딩하는 역량은, 매일 하는 업무가 아니라 판단력을 유지하기 위한 훈련이 될 가능성이 높다.

사이드프로젝트나 개인 학습 시 의도적으로 AI를 내려놓고 처음부터 끝까지 직접 구현해보는 시간을 만드는게 좋음.

귀찮지. 갈수록 더 하기 싫을거고. 마찰과 고통은 성장이다.

## 왜 라는 질문

문제가 있다고 생각했을 때, 왜 라고 물어보는 것.

- 왜 이 구조를 선택해야되는지
- 다른 구조였다면 어떤 트레이드 오프가 있는건지

즉 여러 선택지 중에서 내가 무엇을 선택하는 것인지에 대한 이해.

## 우리의 역할이 리뷰어라고 해도 본질은 변하지 않는다.

작동하는 코드 vs 유지보수가 용이한 코드
맥락에 맞는 추상화 여부에 대한 판단
감각을 말로 전환하고 이를 AI를 활용해서 구현까지 엮어내는 직관기반 언어화

코드를 만드는거 -> 너도 하고 나도 한다.
그러면 인간의 역량차이는? 만든걸 맥락을 고려해서 이해하고 책임지는 사람.

## AI는 우발적 복잡성은 해결하지만, 본질적인 복잡성은 해결하지 않는다.

우발적 복잡성 -> 도구에서 오는 한계인데 AI는 이걸 잘 해결한다. 반복 패턴, 문법 오류 등등

근데 본질적 복잡성, 즉 문제 자체에 내재되어 있는 복잡성은 AI 도구가 해결할 수 없음.

이번에도 Codex 교육자료 만들면서 비슷한걸 느꼈다.

2가지를 해결해야 교육 자료를 만들 수 있음.
- 커리큘럼을 어떤 자료로 전환할지에 대한 결정
- 그 자료를 어떻게 웹사이트 형식으로 구현할지에 대한 문제

근데 후자는 AI가 너무 쉽게 해결해줌. 대부분의 시간을 기획에 썼어야 했고. 이는 본질적인 문제였음. 

'Codex를 아예 모르는 사람을 쉽게 이해시켜서 온보딩 시킨다.'라는 문제를 어떻게 해결할 것인가?

웹사이트를 어떻게 만들지는 본질적인게 아님. 그거는 그냥 기술적인 문제였고.

이런걸 깎는게 맞나? 아니면 뭐가 됐든 바뀌지 않는, AI가 코드를 생산하고 인간이 검수하고 책임지는 구조에서 요구되는 역량을 쌓는게 맞나. 생각해볼 거리다.

# [더이상 성장하지 않는 개발자들](https://evan-moon.github.io/2026/04/18/developers-who-stopped-growing-in-ai-era/)

 `AI가 코드 작성의 고통을 대신해주는 시대가 도래하면서 10년 동안 1년짜리 경험을 반복하는 경로에 빠지기가 이전과는 비교할 수 없이 쉬워졌다.`

AI 시대에 필요한 역량 -> AI 산출물을 평가하고 수정하고 개선하는 것.

근데 AI를 쓰면 쓸수록? 역설적으로 AI 시대에 필요한 역량은 감소한다.


## AI를 잘 쓰려면 좋은 코드를 작성할 줄 알아야 한다.

뭔가 이상한데 -> 수 많은 시행착오와 경험으로 생기는 직관같은 것.

`AI 활용법을 학습하는 것과 코드 패턴을 학습하는 것은 양자택일의 관계가 아니다.`

AI없이도 코드를 판단할 수 있어야 AI를 가장 잘 활용할 수 있는데, AI에만 의존하면 그 판단력은 형성되지 않음.


## 뇌과학 관점에서 이 현상을 바라본다면

`바람직한 어려움` -> 학습 과정에서 적절한 수준의 난이도와 저항이 존재할 때, 단기적인 수행 속도는 느려지지만 장기적인 기억 보존과 전이는 오히려 향상된다.
인출 연습 -> 스스로 기억을 떠올려 보는 것이 장기 기억 형성이 더 도움이 됨.

능동적인 학습이 중요하다. 그 과정에서 불편해야되고, 편하게 받아들인 정보는 쉽게 사라짐.


## 코드를 판단하는 능력은 어떻게 형성되는가?

코딩이라는 것에 대한 직감은 대부분 절차 기억에 의존할 가능성이 높다. `어떻게 하는가`에 대한 기억.

특정 문제를 해결하는 패턴

코드를 보는 순간 단일 책임 원칙의 위반을 감지하는 것.


## 반복적인 수행

반복적으로 해서 뇌 안에서 이 구조가 강화되면 어느순간 생각과 에너지를 조금 소모해서 할 수 있음.

운동과 마찬가지로 코드 훈련을 하면 된다.

## 패턴의 체화

특정 패턴을 반복적으로 마주하다보면 코드에 대해서 여러 패턴을 인식하게 됨.

그래서 이게 체화가 되어야지 구조적 문제를 빠르게 포착할 수 있다.

## 본질적 부하의 필요성

AI가 구현을 대신하면 사실 뇌에는 거의 남는게 없게 됨.

최종 목표만을 AI에게 명시하면? 그 목표를 어떻게 달성했는지를 이해하고 검토하는 능력을 키울 수가 없겠지.

코드를 직접 만들어보면서 인지적 부하가 걸리고 해결해보는 경험이 있어야한다.

## 전부 귀찮지만 학습은 생산과는 다른 접근법이 필요하다.

뇌에 무엇을 남길 것인가?

## 정리하자면...

인지적 부하가 사라지면 뇌는 성장하지 않는다. 

근데 AI는 인지적 부하를 엄청 낮춰준다. 전례없이 그걸 제거한 인류 역사상 최초의 도구가 아닌지...

`고통은 성장의 관점에서 보면 선택이 아니라 조건에 가깝다`

편하게 일하는 것 vs 편하게'만' 일하는 것.
